This is the entire interface.

No web dashboard. No control panel. You type a slash command in Discord and music happens. Here is a real session, playing out.

# general / 🔊 music ONLINE
NOW PLAYING 0:00 / 0:00

Meanwhile the bot's own Discord status reads Listening to —, refreshed every 3 seconds.

02 / INSTRUCTION SET

Seventeen commands.
All prefixed t, so nothing collides.

Every one of them registered to your server, appearing in Discord's autocomplete within a minute of deploying.

/tplay

PLAYBACK

<YouTube URL or search>

Plays something right now. Interrupts the current song but keeps everything queued behind it — your lineup survives.

/tqueue

QUEUE

[YouTube URL or search]

With text, adds to the end. Without, prints what's playing and the next ten up. Two jobs, one verb.

/tskip

PLAYBACK

Next track. In artist mode with an empty queue it fetches a fresh song before skipping, so you never land in silence.

/tremove

QUEUE

<position>

Drops one queued song by the number shown in /tqueue. Everything else stays put.

/tloop

PLAYBACK

Loops the current track. Single track only — looping one song is what people actually want.

/tstoploop

PLAYBACK

Turns looping off. The current song finishes, then the queue picks up where it left off.

/tpause

PLAYBACK

Pauses. The bot stays in the channel — pausing isn't leaving.

/tresume

PLAYBACK

Resumes. Deliberately not a toggle — you can't see the current state, so an explicit verb is always safe.

/tnowplaying

QUEUE

Track, progress bar, who asked for it, and every mode currently on. The one place to find out why it keeps playing music.

/treplay

SESSION

Plays the previous track again. Steps backwards through playback order, not the session record.

/trandom

SESSION

Random pick from what tonight has already played — filtered so it never picks the song currently playing.

/thistory

SESSION

The last 15 tracks this session, newest first, with the current one marked so it doesn't read as a duplicate.

/tartist

DISCOVERY

<artist name>

Artist mode. Every time the queue runs dry, another song by that artist appears. It searches with four different phrasings at random and filters against what you've already heard — three stacked sources of variation, because one wasn't enough to stop it feeling repetitive.

/tstopartist

DISCOVERY

Artist mode off. Handled before the queue check, because the mode outlives the queue.

/trelated

DISCOVERY

Queues something near what's playing. Not a similarity model — it asks YouTube the way a person would: "songs like ___".

/tclear

QUEUE

Empties the queue, keeps the current song. Counts first, so the confirmation tells you exactly how much vanished.

/tstop

PLAYBACK

Full stop. Clears artist mode, deletes the queue, leaves the channel, wipes the session. Three lines that reset six things.

Nothing matches that.

03 / SIGNAL CHAIN

Typed word to sound,
in eight hops.

Every box is a real dependency doing one job. Nothing here is a framework — it's a chain you can follow end to end.

  1. Discord

    You type /tplay in a voice channel.

  2. Gateway

    A WebSocket held open for the life of the process. Close it and the bot is gone.

  3. Router

    One handler in index.js. Checks you're in voice, defers the reply.

  4. Normalize

    Strips Discord's markdown, rebuilds the URL from the video ID, drops &list=.

  5. yt-dlp

    Searches, then returns a direct audio URL. Never downloads a file.

  6. discord-player

    Owns the queue, the history, the progress bar, the idle timeout.

  7. ffmpeg

    Transcodes to Opus. The only part of this that costs real CPU.

  8. Voice

    UDP stream into the channel. Sound.

STATE

Three Maps keyed by server ID — queue, session history, artist mode. Capped at 50 tracks. Nothing is written to disk. Restart the bot and the session is gone, which is exactly what a session should do.

SAFETY

Every playback call gets one retry, 1.5 seconds apart. Not five — more retries at a service deciding whether you're a robot makes things worse, not better.

IDLE

Queue ends, five minutes pass with nothing added, the bot leaves on its own. Long enough to argue about the next song. Short enough not to lurk.

04 / FIELD REPORT

The cloud was the obvious answer.
It was the wrong one.

This bot ran on AWS. Everything worked except the thing it exists to do. What follows is the actual evidence, and what it cost to find.

REVERTED

AWS EC2 t3.micro

Ubuntu 24.04, Node via nvm, ffmpeg via apt. Login, command registration and voice connection all worked first try.

  • Direct YouTube URL3 / 3 succeeded
  • Plain-text searchrepeated failures
  • Search, with retrystill failed

One track failed on both the attempt and the retry — for a URL yt-dlp had resolved correctly seconds earlier.

WHY
CURRENT

Raspberry Pi 4 1GB

Pi OS Lite, Ethernet, in a case, on home internet. One Node process, one ffmpeg transcode at a time, 1GB is plenty.

  • IP rangeresidential
  • Cost after hardwarepennies of power
  • Depends onhome power + internet

A real trade: no snapshots, no failover, and a power cut takes it down. Accepted knowingly.

THE FINDING

YouTube treats datacenter IPs differently from home connections — and the search endpoint is guarded far more heavily than the video one.

The direct-URL path fires two requests. The search path fires three. On a flagged AWS address, that one extra request was the difference between working and not. It never presented as a block — just intermittent, inconsistent failure that reads exactly like a bug in your own code. It wasn't fixable in code, so the fix was a different address.

Two changes made during the investigation survived the rollback: searching through yt-dlp instead of the extractor's own API, and the retry wrapper. Neither was AWS-specific — both replaced something fragile with something better. When an experiment fails, the changes still need sorting into scaffolding and genuine improvement. Throwing out both is the easy mistake.

ALSO ASKED

"The landing page is free on Cloudflare — why not the bot too?" Because this page is files and the bot is a process. It holds a WebSocket open forever, spawns ffmpeg and yt-dlp as real binaries, and streams live UDP. Serverless does none of those. Cloudflare Containers can hold a process open — but that platform scales workloads across regions, and this needs exactly one instance alive in one place forever. Two of these bots means double commands and a fight over the voice channel.

05 / INSTALLATION

Running in five steps.

Needs Node 18 or newer. Everything else installs itself.

  1. 01

    Create the Discord app

    Developer Portal → New Application → name it TunezBot. Open Bot, hit Reset Token, copy it. Grab the Application ID from General Information — that's your CLIENT_ID.

    The token is the whole security model. Anyone holding it controls your bot. Never paste it into a doc, a screenshot, or a commit.

  2. 02

    Get your server ID

    Discord → Settings → Advanced → Developer Mode on. Right-click your server icon → Copy Server ID.

  3. 03

    Fill in .env

    Copy .env.example to .env and drop your three values in. .env is gitignored; the example file ships blank on purpose.

    DISCORD_TOKEN=your_bot_token_here
CLIENT_ID=your_application_client_id_here
GUILD_IDS=your_discord_server_id_here

    GUILD_IDS takes a comma-separated list if you want a test server too.

  4. 04

    Invite it

    OAuth2 → URL Generator. Scopes bot and applications.commands. Permissions: View Channels, Send Messages, Connect, Speak, Use Voice Activity. Open the generated link and pick your server.

  5. 05

    Register and run

    npm install
npm run deploy
npm start

    install once. deploy only when commands change. start every time you want it online — and the terminal running it has to stay open. That constraint is the entire reason a Raspberry Pi got involved.

    /tplay never gonna give you up
